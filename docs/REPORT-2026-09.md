# sitio.com.py — Improvement report (2026-09-11)

> Written by the planning session that produced `plan.md` and `prompts/`. Read this
> once for the reasoning; the decisions themselves live in `plan.md` §1 and are
> not re-litigated by build sessions.

## 1. Where the repo stands

Thirteen PRs merged. Fas 1 (MVP) is complete and fas 2 is two modules in
(`gallery`, `menu`). The build is healthy on this branch:

| Check | Result |
|---|---|
| `npm run typecheck` | clean |
| `npm run lint` | clean |
| `npm run build` | clean, 20 routes |
| `npm audit --omit=dev` | 1 critical (next), 2 high (sharp, postcss) |
| Automated tests | Playwright smoke only (75 checks, needs MySQL) |

The code quality is high for a 14k-line app: every mutation goes through
`requireRole()` and a tenant filter, ISR is used correctly, the analytics
ingest is written defensively, secrets are HMAC'd, and every non-obvious
decision is commented in place. The two remaining risks are not in the code
that exists; they are in what does not exist yet and in what has never run
outside a container.

## 2. Findings, ranked by what they cost if ignored

### F1 — Not deployed. Nothing has run on Hostinger (blocking revenue)

Every "not yet verified" item in `docs/HANDOVER.md` is the same item: deploy
step A has not happened. Uploads persistence over redeploy, the database
timezone, hPanel cron reaching the rollup route, and build memory on the node
are all unknown. This is a human-inputs item (§7 of `plan.md`), not a code
phase. Nothing in this plan should wait for it, and nothing in this plan
should be considered "done" for the customer until it has happened.

### F2 — The root page is the create-next-app boilerplate (visible defect)

`src/app/page.tsx` still renders the Vercel template with "To get started,
edit page.tsx". It is indexable, it is what `sitio.com.py/` will show, and
`docs/PLAN.md` D5 decides the root is the SaaS sales page. This is the first
thing a customer sees if they type the domain. Fix: phase O2.

### F3 — Vulnerable production dependencies, one of them on the upload path

`sharp` 0.35.3 carries inherited libvips and libheif CVEs. Sharp is what
decodes every customer-uploaded image, including HEIC from iPhones, so this
is the one advisory that matters. `next` 15.5.x has a critical advisory for
the image optimizer with AVIF input; the app avoids `next/image` for customer
media but the optimizer route still exists. Both fix by a patch bump. Fix:
phase O1.

### F4 — No unit tests for the pure logic the business rules depend on

`hours.ts` (open-now in Asunción), `format.ts` (phone normalisation, Gs
formatting), `slug.ts`, `billing.ts` (grace/expired lifecycle, day math),
`analytics.ts` (bot classification, referrer stripping), `rollup.ts` day
ranges and `media.ts` path-traversal guard are all pure functions with zero
tests. The smoke test needs a running MySQL and a built app, so it is not
what a session reaches for while editing `billing.ts`. A vitest suite of
these runs in under two seconds and belongs in the pre-push hook. Fix: O1.

### F5 — AI polish ("Pulir textos") is unbuilt, and it is the doorway-page defence

`docs/PLAN.md` §1.4 and §5.1 say the largest architectural risk is 200
structurally identical pages on one domain, and the mitigation is AI-unique
copy per site. `ANTHROPIC_API_KEY` is already in `.env.example` and
`aiPolishedAt` is in the schema, but nothing calls the API. Every site
published before this exists is published with the customer's raw text or
your hand edits. Fix: phase O3.

### F6 — Products module (PR-14) is specified and not built

`docs/HANDOVER.md` already contains the exact recipe (copy the menu chain).
The schema has the table. `modules.ts` still says `plannedIn: "PR-14"`, so
admin correctly shows it as unbuilt. Fix: phase S1.

### F7 — Three of six themes fall back to `servicios`

`salud`, `belleza`, `taller` render the industrial theme. A clínica getting a
dark industrial site is a sales problem, not a bug, but it halves the
"branschanpassat" pitch. Each theme is a self-contained directory plus four
palette entries, which makes them ideal parallel Sonnet work. Fix: S2–S4.

### F8 — The upsell radar (PR-16) is the point of the analytics

`hotLead`, `upsellScore`, `leadStage` and the `HOT_LEAD_*` env thresholds are
all in place and nothing writes them. The dashboard nav has a comment
reserving the slot. Fix: S5.

### F9 — Small security and hygiene items

- `/api/cron/rollup` accepts the secret as `?key=` in the query string, which
  lands in access logs. Remove the query form; keep the bearer header.
- No security headers (`X-Frame-Options`, `Referrer-Policy`,
  `X-Content-Type-Options`, `Permissions-Policy`) in `next.config.ts`. A
  full CSP is out of scope while the themes use inline scripts.
- `.gitignore` lists `drizzle/0000_violet_squadron_supreme.sql` even though
  the file is tracked. Harmless today, confusing tomorrow. Remove the line.
- `scripts/smoke-e2e.mjs` is one 540-line file. Parallel phases cannot both
  append to it. Split the login/launch helpers into `tests/smoke/_lib.mjs`
  and let each phase add its own `tests/smoke/<phase>.mjs`.
- `docs/HANDOVER.md`, `docs/PLAN.md` §3 and `README.md` all carry build
  state. From this round on, `plan.md` §9 and `docs/log/<phase>.md` are the
  only state; HANDOVER.md is retired by the link pass.

All of F9 is folded into O1 except the HANDOVER retirement (S6).

### F10 — Things that are fine and should not be "improved"

- In-memory rate limits and the lazy rollup are correct for one Node process;
  they are documented as such. Do not move them to the DB until a second
  process exists.
- 308 instead of 301 on slug redirects. Google treats them alike.
- Superadmin cannot edit the owner's menu. Deliberate; see HANDOVER.
- `next/image` is not used for customer media. Deliberate and right for
  Hostinger.
- No GitHub Actions. Policy, see `docs/RUNNER-POLICY.md`. This plan adds none.

## 4. The shape of the plan

Nine phases, two lanes, one PR each, following the `phased-autonomous-build`
method. Lane 1 is three sequential Opus phases (hardening and test harness,
landing page, AI polish) because each creates something later phases build
on or is a new layout. Lane 2 is five parallel Sonnet phases that each own
their own directory, plus a Sonnet link pass. Model per phase is decided in
`plan.md` and never by the session. Fable does not appear in the phase table
(`fable-cost-guardrail`).

Expected cost: about $35 for lane 1, about $45 for lane 2 and the link pass,
roughly $80 total and about 5 hours wall-clock with lane 2 in parallel.
Anything over $110 is a process failure to write into the skill's Budget
section, not a fact of life.
